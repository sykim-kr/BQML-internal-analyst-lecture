    Query 1 — CREATE MODEL

    읽는 포인트

    • data_split_method='NO_SPLIT'은 이번 demo에서 흐름을 단순하게 보여주기 위한 설정입니다.
    • 대신 WHERE user_id != 156으로 특정 사용자를 예측 대상으로 남겨둡니다.
    • 실제 운영 검증에서는 AUTO_SPLIT, RANDOM split, 별도 evaluation table을 권장합니다.
    • 핵심은 학습 데이터와 예측/평가 대상을 섞지 않는 것입니다.
    CREATE OR REPLACE MODEL `...bqml_course_game_revenue_model_v0`
OPTIONS(
  model_type = 'LINEAR_REG',
  input_label_cols = ['purchase_amount'],
  data_split_method = 'NO_SPLIT'
) AS
SELECT
  game_time,
  login_count,
  level_achieved,
  purchase_amount
FROM `...bqml_course_game_data`
WHERE user_id != 156;

    FP구매할 거라 예측했는데, 예측 실패 (구매 안함)늑대다라고 외쳤는데, 안나타남음성을 양성으로 판정스팸 아닌데 스팸이라 함

    TN구매안할 거라 예측했는데, 실제로도 구매 안함늑대 안 온다고 하고, 실제로도 늑대 안홈음성을 음성으로 판정스팸 아닌 건 스팸 아닌 걸로 분류

    TP (구매O,예측성공)FP (구매X,예측실패)FN(구매O,예측실패)TN(구매X,예측성공)
    755515
    accuracy — 정확도는 분류 모델이 바르게 된 예측의 비율입니다. (예측 성공 비율 = (TP+TN)/N=90%)
    precision — 분류 모델의 통계입니다. 정밀도는 모델이 포지티브 클래스를 정확히 예측한 빈도를 나타냅니다. (구매할 것이다라는 걸 정확히 짚어냄. 구매 예측 성공 비율(TP/N)=75%)
    recall — '가능한 모든 포지티브 라벨 중에서 모델이 정확히 몇 개를 식별했을까'라는 질문의 답변을 제공하는 분류 모델의 통계입니다. (구매가 O인 경우 중 예측 성공한 경우, TP/TP+FN=75/80=93.8%)
    f1_score — 모델 정확도를 나타내는 척도입니다. f1 점수는 정밀도와 재현율의 조화 평균입니다. f1 점수는 1이 가장 좋은 값입니다. 가장 나쁜 값은 0입니다.
    log_loss — 로지스틱 회귀에 사용된 손실 함수입니다. 모델 예측이 올바른 라벨과 얼마나 차이가 나는지를 나타내는 척도입니다.
    roc_auc — AUC(ROC 곡선 아래 영역)입니다. 이것은 분류 기준에서 임의로 선택한 양의 예가 실제로 양수인 것이 임의로 선택한 음의 예가 양수인 것보다 더 확실할 확률입니다.

      Classification evaluation logic — TP/FP/FN/TN

      Before metrics, first draw the 2x2 logic.
      Business reading:
      TP: 구매/이탈/위험이 실제 O이고, 모델도 O라고 맞힘
      FP: 실제는 X인데, 모델이 O라고 잘못 찍음
      FN: 실제는 O인데, 모델이 X라고 놓침
      TN: 실제 X이고, 모델도 X라고 맞힘
      FP는 불필요한 캠페인/CS 비용을 만든다.
      FN은 실제 위험 고객을 놓쳐 매출/리텐션 손실을 만든다.
      그래서 평가는 “정답률”이 아니라 “어떤 실수를 더 줄일 것인가”의 결정이다.

      분류 모델 평가 지표 지도

      예시 confusion matrix값
      N100
      TP75
      FP5
      FN5
      TN15
      accuracy = (TP + TN) / N = 90% — 전체 정답률
      precision = TP / (TP + FP) = 75 / 80 = 93.8% — 찍은 대상이 실제 positive일 가능성
      recall = TP / (TP + FN) = 75 / 80 = 93.8% — 실제 positive를 놓치지 않는 정도
      f1_score — precision과 recall의 균형점
      log_loss — 예측 확률이 실제 정답과 얼마나 어긋났는지
      roc_auc — threshold를 바꿔도 양성과 음성을 잘 구분하는지
      29

      평가 지표를 액션 비용으로 읽기

      상황우선 지표이유
      캠페인 비용이 낮고 놓치면 손실이 큰 경우recall 중심위험/기회 고객을 놓치지 않는 것이 중요합니다.
      CS·상담·고비용 오퍼처럼 개입 비용이 큰 경우precision 중심잘못 찍은 대상에게 비용을 쓰지 않는 것이 중요합니다.
      전체 모델 비교나 균형 확인f1_score / roc_auc정밀도와 재현율의 균형, threshold 전반의 구분력을 함께 봅니다.

      평가는 숫자 맞히기가 아니라, 어떤 실수를 줄일지 결정하는 과정입니다.

      New Section

      Section 5. 변수 설계 — 모델은 변수를 통해 세상을 봅니다

      알고리즘보다 먼저, 모델이 읽을 수 있는 행동 신호를 설계합니다.

      48

      왜 변수 설계가 중요한가

      • 모델은 비즈니스 맥락을 스스로 이해하지 못합니다.
      • 모델이 실제로 보는 것은 feature table의 변수뿐입니다.
      • 좋은 질문 → 좋은 변수 → 해석 가능한 예측 순서가 중요합니다.
      • 성능을 보장하는 마법 공식이 아니라, 행동 신호를 잘 번역하는 설계 과정입니다.

      모델 성능은 알고리즘보다 변수가 먼저 결정합니다.

      49

      변수 유형을 먼저 구분합니다

      유형예시강의 포인트
      범주형device_type, traffic_source, membership_type그룹 차이를 표현합니다. category가 너무 많으면 상위값/기타 처리가 필요합니다.
      이진is_payer, is_inactive_14d, completed_tutorial0/1이라 해석이 쉽고 액션과 연결하기 좋습니다.
      순서형level_tier, engagement_stage, risk_band순서는 있지만 1/2/3 간격이 같다는 뜻은 아닙니다.
      연속형 숫자total_playtime_minutes, login_count_7d, days_since_last_login값 그대로도 쓰지만 구간/threshold/ratio로 행동 의미를 보강합니다.
      파생 변수avg_playtime_per_login, playtime_segment, playtime_drop_rate데이터를 모델의 언어로 번역합니다.
      50

      연속형 숫자 변수: 그대로 쓸까, 나눌까?

      Raw numeric: total_playtime_minutes, login_count_7d처럼 정보 손실 없이 행동량을 넣습니다.
      Binning: no_play / light / medium / heavy처럼 행동 강도 구간으로 바꿉니다.
      Threshold flag: days_since_last_login >= 14, purchase_count_30d >= 3처럼 후보 신호를 만듭니다.
      핵심: 숫자는 값이면서 동시에 행동 신호입니다.
      51

      Threshold는 자동 배제 규칙이 아닙니다

      • Threshold는 분석·실험·우선순위 판단을 돕는 설명 가능한 후보 신호입니다.
      • days_since_last_login >= 14 → 재방문 유도 실험 후보 신호
      • purchase_count_30d >= 3 → 반복 구매 행동 신호
      • total_playtime_minutes >= 60 → 일정 수준 이상 몰입 경험 신호
      • support_ticket_count >= 2 → 추가 케어/지원 우선순위 신호
      • 실제 기준값은 분포, 성과, 현업 맥락으로 검증해야 합니다.

      자동 조치·제외·차단 기준이 아니라 검토·실험·우선순위 후보 신호입니다.

      52

      비선형 신호를 포착합니다

      • 고객 행동은 항상 직선적으로 증가하지 않습니다.
      • login_count 0→3회 증가는 큰 행동 변화일 수 있지만, 20→23회 증가는 추가 의미가 작을 수 있습니다.
      • raw numeric만으로는 구간별 행동 의미 차이가 약하게 표현될 수 있습니다.
      • bucket / threshold / ratio는 행동 단계가 바뀌는 지점을 모델이 볼 수 있게 돕습니다.
      • 단, 구간이 너무 많으면 해석 혼란과 과적합 위험이 있습니다.

      숫자의 크기뿐 아니라, 행동 단계가 바뀌는 지점을 모델이 볼 수 있게 만드는 것이 변수 설계입니다.

      53

      BQML Game/Churn Feature Table 예시

      읽는 포인트

      • feature table은 모델이 읽는 행동 신호 사전입니다.
      • raw numeric, ratio, threshold flag, bucket을 함께 설계합니다.
      • threshold_flag는 자동 조치가 아니라 검토·실험 후보 신호입니다.
      • label인 churned와 feature의 시간 순서가 섞이지 않도록 주의합니다.
      SELECT
  user_id,
  total_playtime_minutes,         -- raw numeric: 행동량
  login_count_7d,
  purchase_count_30d,
  days_since_last_login,
  SAFE_DIVIDE(total_playtime_minutes, NULLIF(login_count_7d, 0))
    AS avg_playtime_per_login,     -- ratio: 로그인 1회당 평균 플레이 시간
  IF(days_since_last_login >= 14, 1, 0)
    AS is_inactive_14d,            -- 검토·실험 후보 신호
  IF(purchase_count_30d >= 3, 1, 0)
    AS is_repeat_purchaser,        -- 반복 구매 행동 신호
  CASE
    WHEN total_playtime_minutes = 0 THEN 'no_play'
    WHEN total_playtime_minutes < 60 THEN 'light'
    WHEN total_playtime_minutes < 300 THEN 'medium'
    ELSE 'heavy'
  END AS playtime_segment,
  churned
FROM sample_game_user_features;
      54

      변수 설계를 액션으로 연결합니다

      Feature모델이 읽는 신호액션 연결
      is_inactive_14d14일 이상 미접속 후보 신호재방문 유도 실험 후보군 검토
      is_repeat_purchaser최근 30일 반복 구매 행동멤버십/번들 오퍼 실험 후보
      playtime_segment플레이 강도 구간온보딩/몰입도별 메시지 차등 설계
      avg_playtime_per_login로그인 1회당 몰입도짧은 방문/깊은 사용 패턴 구분
      support_ticket_count지원 접점 증가 신호추가 케어/지원 우선순위 판단 보조

      Worksheet 4 — Feature Table 설계 실습

      • Part 1. 변수 유형 분류: device_type, login_count_7d, total_playtime_minutes, purchase_count_30d, days_since_last_login, completed_tutorial, churned를 분류합니다.
      • 분류 기준: 범주형 / 이진 / 순서형 / 연속형 / 파생 가능 / 타깃
      • Part 2. churn 예측용 feature 10개를 설계합니다.
      • 작성 항목: 변수명 / 변수 유형 / 계산 방식 / 예측에 도움 되는 이유
      • 표현 방식 선택: raw numeric / bucket / threshold flag / ratio 중 무엇으로 표현할지 적습니다.
      • 가능한 실험·리텐션·지원 액션 후보를 함께 적습니다.
      • leakage 위험 여부: 예측 시점에 알 수 없는 정보나 타깃 이후 정보가 섞였는지 확인합니다.
      • 각 threshold가 자동 조치 기준이 아니라 어떤 검토·실험·우선순위 후보 신호인지 적습니다.
      • feature table에서 제외해야 할 민감속성/직접 식별자/누수 변수를 표시합니다.

      좋은 feature table은 모델 결과를 액션 언어로 번역할 수 있게 만듭니다.

      56

      Section 5 핵심 정리

      • 모델은 변수로 세상을 봅니다.
      • 연속형 숫자는 raw / bucket / threshold / ratio로 설계할 수 있습니다.
      • threshold는 자동 배제 기준이 아니라 설명 가능한 후보 신호입니다.
      • 파생 변수는 데이터를 모델의 언어로 번역하는 작업입니다.
      • 예측 모델링의 출발점은 알고리즘 선택이 아니라 feature table 설계입니다.
