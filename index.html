CREATE OR REPLACE MODEL `...bqml_course_game_revenue_model_v0`OPTIONS(  model_type = 'LINEAR_REG',  input_label_cols = ['purchase_amount'],  data_split_method = 'NO_SPLIT') ASSELECT  game_time,  login_count,  level_achieved,  purchase_amountFROM `...bqml_course_game_data`WHERE user_id != 156;

Classification evaluation logic — TP/FP/FN/TN

• Before metrics, first draw the 2x2 logic. • Business reading: • TP: 구매/이탈/위험이 실제 O이고, 모델도 O라고 맞힘 • FP: 실제는 X인데, 모델이 O라고 잘못 찍음 • FN: 실제는 O인데, 모델이 X라고 놓침 • TN: 실제 X이고, 모델도 X라고 맞힘 • FP는 불필요한 캠페인/CS 비용을 만든다. • FN은 실제 위험 고객을 놓쳐 매출/리텐션 손실을 만든다. • 그래서 평가는 “정답률”이 아니라 “어떤 실수를 더 줄일 것인가”의 결정이다.

27

원본 p14 — 회귀 평가: 설명력과 오차 구조

실제 관측 값과 예측 값 간의 상관 계수를 구한 다음 제곱해서 구함

SSR = (예측값 - 평균)²의 합계

SSE = (관측값 - 예측값)²의 합계

SST = SSR + SSE

해석: 모델이 실제값의 변동을 얼마나 설명하는지 확인합니다.

R² 수식과 실무 해석
R² = 1 - (SSE / SST)
= 1 - (모델이 틀린 정도 / 원래 데이터가 들쭉날쭉한 정도)
예: R²=0.72 → 실제값 변동의 약 72%를 모델이 설명.
높다고 무조건 좋은 모델은 아닙니다. 과적합·데이터 누수·업무상 허용 오차를 함께 봅니다.

왜 변수 설계가 중요한가

모델은 비즈니스 맥락을 스스로 이해하지 못합니다.

모델이 실제로 보는 것은 feature table의 변수뿐입니다.

좋은 질문 → 좋은 변수 → 해석 가능한 예측 순서가 중요합니다.

성능을 보장하는 마법 공식이 아니라, 행동 신호를 잘 번역하는 설계 과정입니다.

모델 성능은 알고리즘보다 변수가 먼저 결정합니다.

49

변수 유형을 먼저 구분합니다

유형예시강의 포인트
범주형device_type, traffic_source, membership_type그룹 차이를 표현합니다. category가 너무 많으면 상위값/기타 처리가 필요합니다.
이진is_payer, is_inactive_14d, completed_tutorial0/1이라 해석이 쉽고 액션과 연결하기 좋습니다.
순서형level_tier, engagement_stage, risk_band순서는 있지만 1/2/3 간격이 같다는 뜻은 아닙니다.
연속형 숫자total_playtime_minutes, login_count_7d, days_since_last_login값 그대로도 쓰지만 구간/threshold/ratio로 행동 의미를 보강합니다.
파생 변수avg_playtime_per_login, playtime_segment, playtime_drop_rate데이터를 모델의 언어로 번역합니다.
50

연속형 숫자 변수: 그대로 쓸까, 나눌까?

Raw numeric: total_playtime_minutes, login_count_7d처럼 정보 손실 없이 행동량을 넣습니다.

Binning: no_play / light / medium / heavy처럼 행동 강도 구간으로 바꿉니다.

Threshold flag: days_since_last_login >= 14, purchase_count_30d >= 3처럼 후보 신호를 만듭니다.

핵심: 숫자는 값이면서 동시에 행동 신호입니다.

51

Threshold는 자동 배제 규칙이 아닙니다

Threshold는 분석·실험·우선순위 판단을 돕는 설명 가능한 후보 신호입니다.

days_since_last_login >= 14 → 재방문 유도 실험 후보 신호

purchase_count_30d >= 3 → 반복 구매 행동 신호

total_playtime_minutes >= 60 → 일정 수준 이상 몰입 경험 신호

support_ticket_count >= 2 → 추가 케어/지원 우선순위 신호

실제 기준값은 분포, 성과, 현업 맥락으로 검증해야 합니다.

자동 조치·제외·차단 기준이 아니라 검토·실험·우선순위 후보 신호입니다.

52

비선형 신호를 포착합니다

고객 행동은 항상 직선적으로 증가하지 않습니다.

login_count 0→3회 증가는 큰 행동 변화일 수 있지만, 20→23회 증가는 추가 의미가 작을 수 있습니다.

raw numeric만으로는 구간별 행동 의미 차이가 약하게 표현될 수 있습니다.

bucket / threshold / ratio는 행동 단계가 바뀌는 지점을 모델이 볼 수 있게 돕습니다.

단, 구간이 너무 많으면 해석 혼란과 과적합 위험이 있습니다.

숫자의 크기뿐 아니라, 행동 단계가 바뀌는 지점을 모델이 볼 수 있게 만드는 것이 변수 설계입니다.

53

BQML Game/Churn Feature Table 예시

읽는 포인트

  • feature table은 모델이 읽는 행동 신호 사전입니다.
  • raw numeric, ratio, threshold flag, bucket을 함께 설계합니다.
  • threshold_flag는 자동 조치가 아니라 검토·실험 후보 신호입니다.
  • label인 churned와 feature의 시간 순서가 섞이지 않도록 주의합니다.

SELECT user_id, total_playtime_minutes, -- raw numeric: 행동량 login_count_7d, purchase_count_30d, days_since_last_login, SAFE_DIVIDE(total_playtime_minutes, NULLIF(login_count_7d, 0)) AS avg_playtime_per_login, -- ratio: 로그인 1회당 평균 플레이 시간 IF(days_since_last_login >= 14, 1, 0) AS is_inactive_14d, -- 검토·실험 후보 신호 IF(purchase_count_30d >= 3, 1, 0) AS is_repeat_purchaser, -- 반복 구매 행동 신호 CASE WHEN total_playtime_minutes = 0 THEN 'no_play' WHEN total_playtime_minutes < 60 THEN 'light' WHEN total_playtime_minutes < 300 THEN 'medium' ELSE 'heavy' END AS playtime_segment, churned FROM sample_game_user_features;

Worksheet 4 — Feature Table 설계 실습

• Part 1. 변수 유형 분류: device_type, login_count_7d, total_playtime_minutes, purchase_count_30d, days_since_last_login, completed_tutorial, churned를 분류합니다. • 분류 기준: 범주형 / 이진 / 순서형 / 연속형 / 파생 가능 / 타깃 • Part 2. churn 예측용 feature 10개를 설계합니다. • 작성 항목: 변수명 / 변수 유형 / 계산 방식 / 예측에 도움 되는 이유 • 표현 방식 선택: raw numeric / bucket / threshold flag / ratio 중 무엇으로 표현할지 적습니다. • 가능한 실험·리텐션·지원 액션 후보를 함께 적습니다. • leakage 위험 여부: 예측 시점에 알 수 없는 정보나 타깃 이후 정보가 섞였는지 확인합니다. • 각 threshold가 자동 조치 기준이 아니라 어떤 검토·실험·우선순위 후보 신호인지 적습니다. • feature table에서 제외해야 할 민감속성/직접 식별자/누수 변수를 표시합니다.

Section 5 핵심 정리

모델은 변수로 세상을 봅니다.

연속형 숫자는 raw / bucket / threshold / ratio로 설계할 수 있습니다.

threshold는 자동 배제 기준이 아니라 설명 가능한 후보 신호입니다.
